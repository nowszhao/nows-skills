# 问题审计手册｜如何发现真正重要但未充分回答的问题

## 1. 与“作者提出的问题”分开

- A：作者明示或可由原文论述直接重建的问题，存于 `nodes`，不能制造作者没说过的话。
- B：读者为了理解核心结论、评估可信度、采取行动**必须有答案**的关键追问，存于 `criticalGaps`，标 `origin=reader_inferred`。
- B 可以没有原文直接证据锚点（`evidence: []`），但必须说明触发疑问的核心主张与审阅范围，并把它视为分析者的审查意见。

## 2. 先定义“回答此问究竟需要什么”

| 问题类型 | 充分回答的最低内容 | 典型欠缺 |
|---|---|---|
| 定义/边界 | 清楚定义、对象、排除条件、反例 | 空洞术语、无适用边界 |
| 机制/因果 | 因果链、关键前提、支持证据、替代解释 | “因为有效所以值得信任”循环论证 |
| 方法落地 | 前置条件、输入、步骤/工具、验收结果、失败/回退流程 | 只有“要做”，没有“怎么做” |
| 覆盖/充分性 | 范围清单、要求到测试的映射、遗漏发现方法、验收门槛、残余风险 | 演示几个测试就声称已全面验证 |
| 性能/效果 | 指标定义、基线、样本、评估设计、结果、限制 | 只报产量不报质量 |
| 泛化/ROI | 成本构成、环境条件、规模化瓶颈、适用与不适用场景 | 单人成功推导出所有团队可复制 |
| 观点争议 | 相竞争的解释、各自证据、成立条件 | 把个人观点当行业共识 |

## 3. 深挖“验证让人信任”的两个必问点

**G1 验证是否足够全面？** 检查：目标/正确性定义；从需求与架构风险生成验证清单；正常/异常/边界/安全/性能/回归；需求-测试追踪与覆盖指标；测试本身的错误发现能力；未覆盖风险如何记录与审批；放行/回滚阈值。

**G2 具体如何执行？** 检查：所需环境；步骤和工具配置；每一步预期、实际结果与日志；失败定位、修复、重试；独立复核和自动合并门禁；产物可复查性。

满足 G1 不必意味着数学上证明“绝不遗漏”；工程上更合理的目标是：覆盖范围透明、主要风险有可审计证据、残余风险被接受或继续约束。

## 4. 状态判定

- `full`：针对**这一个明确的问题**，内容齐备且有足够可追溯依据；不意味着独立事实认证。
- `partial`：解决一部分，缺失会实质影响理解/使用。
- `assertion`：主要是判断、承诺或自述，缺可检验支撑。
- `unanswered`：在已审阅材料中未见直接或可重建答案。
- `contradiction`：存在无法调和的实质冲突。
- `unaudited`：素材缺失，或尚未核查此问；不能当成没回答。

始终区分：（a）已述方向但落地不充分；（b）有操作步骤但不证明有效；（c）确有证明但不覆盖目标；（d）资料不足无法核对。

## 5. 缺口价值排序

优先级以“若没有答案，会不会导致读者做错重要判断或无法行动”为第一标准，再看证据与回答缺失程度；不可用新颖度简单替代重要性。

`critical`：不回答则核心命题无法判断或行动存在重大风险。
`high`：显著影响可信度、可复现性或后续实施。
`medium`：影响优化、局部边界或扩展。
`low`：背景性追问，不宜占首页位置。

## 6. 最终问自己

> 即使读者完全不知道这篇材料讲了哪些故事，只看这份报告首页，他能否知道“作者回答了多少”“最关键哪几个问题没答”“缺什么具体证据”“下一步怎么验证”？

如果不能，就不应交付为完整分析。
