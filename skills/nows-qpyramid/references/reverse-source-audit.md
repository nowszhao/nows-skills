# 交付前最后一关：从 HTML 反向核对原文

> 目的不是让生成结果看起来“很完整”，而是审查有损压缩后，**原文最重要的意思是否仍被准确、充分、可追溯地讲清楚**。

这是**必须执行的终审步骤**，不等于一般的检查错别字、验证 JSON 结构或用模型给自己打分。不能因为代码校验通过，就声称语义核对完成。

## 一、先固定一份独立于摘要的“原文要点台账”

在生成 FAQ/HTML **之前**，重新按章节、话题或时间线通读原材料，建立 `source-inventory.json`。它记录：

- 实际读取范围：`scope = full | major_part | excerpt`，以及哪些章节/画面/字幕不可访问；完整材料记录 `sourceExtent`（如 00:00–56:52、1–12 页），非全文则写 `scopeNotes`。只有完整原文确实可取得且全程审阅后才能填 `full`。
- `segments`：原文连续片段及其可定位的页、段或时间码。不能凭摘要猜测缺失段落。每个已读取片段至少对应一条要点；如果全是寒暄/重复，应在该片段的 `exclusionReason` 解释为什么可略去。
- `keyPoints`：要点 ID、在原文的位置、作者真正说了什么、类型、重要程度和原文锚点。类型至少考虑：中心判断、论证理由、具体方法、例子/数据、适用条件、作者的自我限定、反例或相反观点、结论。
- 重要程度：`core`（删掉会误解整篇）、`major`（直接支撑中心论点或关键做法）、`supporting`（辅助案例/背景）、`minor`（重复、闲聊或可舍弃细节）。**不按某段视频时长自动分配重要性。**
- 绝不先看生成的 HTML 再倒推要点，否则会对遗漏盲视。台账在初次分析前形成；生成以后只可以依据新发现的**原文证据**修正台账并注明原因，不能为通过检查删掉原文核心要点。

例如原文强调“可执行验证”而报告只有“验证很重要”，该要点应视为**未充分表达**，不能因为标题含“验证”就算覆盖。

## 二、内容映射：原文 → 报告

逐一取 `source-inventory.json` 的每个要点，打开**已生成的 HTML**，核查它是否真的被讲明白：

1. **存在性**：能否在正文、核心主张、FAQ、洞见或必要的关键追问中找到，而非仅存于 JSON 或隐藏证据片段。
2. **准确性**：主体是谁、说了什么、程度/语气如何、数字和前提是否准确。`may`/`could` 不得翻成确定结论；原文反例不得被删。
3. **充分性**：核心方法是否保留步骤、约束、作用机制及关键案例；只有一句泛泛口号不得算通过。
4. **位置合理**：中心论点是否出现在首页核心主张或重要主线；真正有信息差的具体观点是否显著，而不是淹没在小字 `limits` 中。
5. **压缩合理**：次要材料可省略，但需要注明“有意省略的辅助信息”。`core`、`major` 原则上不能省略；篇幅有限可在 300 字复述中简写，完整细节仍应保留于 FAQ/证据详情。

台账中每条要点标 `disposition: included | omitted`、`reportRefs`、`omitReason`。只有把重要观点**实际写进可见报告并表达充分**才能标 `included`。`evidence` ID 单独存在不计覆盖。

## 三、反向忠实性：报告 → 原文

再从 HTML 出发，不仅检查台账：

- 检查核心主张、独特洞见、300 字复述、每条关键 FAQ 和关键追问中的实质性事实/推论，能否找到原文锚点或明确写成“分析者推断 / 对读者的补充问题”。
- 检查作者观点和分析者建议有没有串台；证据是事实、自述、演示还是比喻。把“可运行/可测量”直接改写成“已证明质量可靠”是错误。
- 核查重要数字、日期、技术名词、否定/转折/条件、讲者归属、复用边界和相互矛盾的段落。
- 追问“如果只看此 HTML，读者会不会得到不同于原文的结论？”；任何误导性新增结论都是 **阻断项**。
- 原始资料若无法再次获取，不能伪称已经完成原文反向核查；只能写“基于现有节选/摘要的有限核对”，必要时请用户提供全文/字幕。

## 四、查错 → 修正 → 重建 → 再查，直到退出门槛满足

**循环条件**：

1. 基于真实原材料和 `source-inventory.json`，查遗漏、失真、错证、主次颠倒和展示隐藏问题。
2. 任何 `core` / `major` 漏项、误导性结论、证据错配、重要边界丢失、HTML 与 JSON 不一致 → 先修分析 JSON，必要时修台账并保留事实依据。
3. 运行 `build_report.py` 生成新的 HTML，打开新版 HTML 检查实际显示内容，**不要只看脚本生成的 JSON**。
4. 重新执行反向核对。**任何修订都会让前一次审核记录失效**；重新生成与新版 HTML 哈希匹配的审核记录。
5. 只有“没有仍未解决的核心/重大问题、语义核对和内容展示通过、能追溯重要主张”才允许交付为“已完成全文核对”。

不得无限循环而声称“百分百零遗漏”。如果材料不可访问、证据矛盾、工具不具备相应能力或合理重试后仍不能解决，则停止、明确列出未通过项和核对范围，**不得冒充通过**；可以交付标明限制的草稿或说明无法完成可靠终审。

## 五、辅助脚本与审核文件

使用 `scripts/check_coverage.py`：

```bash
# 先生成带 HTML/台账哈希的待审核文件（全部 pending）
python scripts/check_coverage.py prepare source-inventory.json analysis.json report.html audit-review.json

# 重新打开原文和 report.html，填完每条要点判断与审核维度后，验证
python scripts/check_coverage.py verify source-inventory.json analysis.json report.html audit-review.json
```

`audit-review.json` 有三层：

- `items`: 每个要点的 `verdict`（pass/fix_needed/unverifiable）与**具体核对理由**；不能统一填写套话。`core`/`major` 需要认真逐项对照。
- `claimChecks`: 自动列出 HTML 的首页主张、复述、各 FAQ、重点洞见、实践点、论证关系、关键追问；逐条填入 `pass/fix_needed/unverifiable`、原文锚点、作者/分析者归属及判断理由。不允许只给一个笼统的“全文核对通过”。
- `checks`：`forwardCoverage`、`reverseFidelity`、`evidenceAttribution`、`priorityAndCompleteness`、`renderedHtml`，均标 pass/fail/unverified，并给核对说明；`renderedHtml` 必须基于实际打开页面的检查，不能用 JSON 合法性代替。若无法浏览器预览，就写 `unverified`。

辅助脚本只检查**引用、覆盖登记、版本哈希与审核状态是否自洽**；它**无法替人判断**同一句话是否忠于原文。语义判断必须在读取原始资料和最终 HTML 后完成，最好在独立的第二轮上下文中进行。脚本通过不能代表“原文已自动完整理解”。

## 六、内部指标（不可假精确）

可按 `core/major/supporting/minor` 统计“已登记且核对通过的要点数”，但这只度量台账所记录的内容，不等于全文真实无遗漏的概率。优先展示漏掉什么、修了什么；不要以“98% 精准”代替审核。审核详情可保留为内部文件，用户默认只收到当前最终版 HTML 与 Skill，不要在 HTML 中堆满审计过程。
