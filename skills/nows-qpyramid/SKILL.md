# Question Pyramid · 知识驾驶舱

你的工作不是把文章压缩成一堆术语，而是帮助读者看明白：**作者究竟想说什么，哪些看法值得记住，各个问题如何得到回答，凭什么这样回答，哪些重要追问还没有答案。**

## 默认交付

- 默认输出 **单文件、可离线打开的交互式 HTML**；仅当用户明确要求其他格式时才调整。使用仓库内 `scripts/build_report.py` 和 `assets/renderer.html`，而非重新发明页面样式。
- 信息顺序固定：**核心主张 → 独特洞见 → 内容复述 → 全展开问题导图（含论证关系与原文）→ 关键追问**。读者先看值得学习的东西，再审视不足；不是专门挑刺。
- **内容复述**必须单列章节，标题就叫“内容复述”。用一段约 **300 个汉字（280–320 个汉字，不计英文和标点）** 的自然中文。**先按重要性筛选原文内容，不平均分配篇幅**：优先交代核心问题与作者的主要回答，其次写 2–4 个最关键的做法、论据或例子，最后用少量篇幅交代必要的条件和局限。可按论证关系组织，不必机械遵循视频时间线。它不是口号、提纲或分析者的评论，不得编造案例、数字和主张。原文没有谈的内容不能写作作者的观点。
- **问题导图始终全展开**：首次加载展示所有主线和具体问题，且用户不能收起分支；点击节点只负责打开答案与证据详情，**必须保持画布平移位置和缩放比例不变**，不得重新生成整张导图、自动居中选中节点或自动调用“适应画面”。只有用户明确拖动、缩放或点击适应画面时才能改变视角；从导图以外的观点卡跳转到节点时，仅在目标位于可视区域外时允许定位。保留拖拽、缩放、搜索、观点筛选和原文跳转。**不得**加入折叠按钮、展开开关、默认隐藏的子节点。关键追问卡片为避免页面过长，仍允许展开详情，二者不能混同。
- 输出给用户时，提供生成的 HTML 和完整 Skill 安装包；如仅分析素材，至少提供 HTML。

## 工作步骤

1. **取得原始材料。** 优先全文、完整字幕/逐字稿、原始页面。记录可读范围及不确定内容；拿到节选不能声称覆盖全文。自动字幕的专有名词、引语归属与时间码必须谨慎核查。
2. **先做原文证据台账。** 顺序标记作者明说的主张、案例、理由、数据、限定条件和原文锚点。不能由常识替作者补论据。长材料依据 `references/long-form-workflow.md` 分段覆盖。
3. **建问题金字塔。** 从核心问题 Q0 下提炼各主线及具体追问；原则上 3 层：根问题、一级主线、叶子问题。保留作者真实的论证顺序和重要分歧，不为凑问题数机械拆句。每个节点写回答、依据、推理、适用边界及 `answerStatus`。
4. **挑选真正有增量的主张。** 聚焦能改变读者认知或行动的具体观点，说明为何不同、证据是什么。**观点新奇不代表正确**。共识、差异性、证据强度和回答充分性独立标注，参见 `references/evidence-taxonomy.md`。
5. **写约 300 字“内容复述”。** 看完全部材料之后再写，不从标题猜、不拼凑 FAQ 句子。先挑出最重要的 3–5 个信息点：中心问题和结论优先；与结论直接相关的关键做法、论据及代表性案例占主要篇幅；必要边界简要说明。按理解价值而非原文篇幅分配字数，删去寒暄、重复、次要细节、无关轶事和模板式评论。不要为了凑满 300 字写无关信息。把作者的讲述与分析者的判断分开；材料有限时用“所读材料中”而不是声称看过完整视频。保存到 `meta.contentRetelling`。
6. **审查关键追问。** 再换到读者视角：要相信它或照做，哪些必要问题还得回答？分类 `full`、`partial`、`assertion`、`unanswered`、`contradiction`、`unaudited`；明确“已说了什么、还缺什么、补充什么证据才能回答充分”。详细判据见 `references/answer-sufficiency.md`。审查依据与原文结论分开记录。
7. **写自然中文。** 按 `references/natural-writing.md`，把套话和抽象名词换成具体动作、对象、结果。问题像真正会问的问题；主张有归属；必要技术词保留，不强行口语化。不在没证据处补全闭环。
8. **生成可验证的 JSON 与 HTML。** 参考 `references/output-contract.md` 和 `examples/Lauren-GrokBot-分析数据.json`，运行：

   `python scripts/build_report.py analysis.json report.html`

   脚本会校验来源、问题树、证据 ID、关键追问和复述字数。页面完全由当前分析 JSON 渲染；不得写死 Lauren Tan 或其他样例作者的内容。

## 中文内容风格（不可省略）

- 少说“赋能、价值闭环、能力底座、构建体系、认知增量雷达”等没有实质内容的抽象话，优先写“做了什么、为什么、发生了什么”。
- 不要机械套“不是……而是……”“真正重要的是……”“本质上……”之类反复出现的句式；若确有必要可偶尔用。
- 不把每个观点包装成颠覆性洞见；不编造原文没有的结论、证据、数字或实施步骤。
- 不为自然表达而扭曲技术细节。`Feature Map`、`CI`、`eval`、`PR` 等必要术语应保留并在需要时解释。
- 长句能拆则拆，标题用清楚的问句，正文有事实、案例和条件；把“作者称”与“分析者推断”分清。
- 参考 Humanizer-zh 的思路，但本 Skill 内的规则必须自足，不依赖在线访问其他仓库。

## 关键质量门槛

- 读者能在前两屏看清作者最重要的判断及 3–5 个具体有价值的观点。
- **“内容复述”须为 280–320 汉字的自然单段复述，覆盖原文最重要的信息，而不是把每一节等比例压缩，也不是要点列表或额外评论。**
- **问题导图全部可见，没有折叠功能；点击任意导图节点前后视角必须保持固定，不能闪动或重置缩放。** 展示受屏幕大小影响时允许通过平移和缩放浏览，不能靠默认隐藏节点减少信息。
- 每个重要问题都能定位到原文；原文没有答案或素材不完整时明说。
- 不靠“作者说过”就推定行业共识；同源转载不算独立核验。
- 非共识观点与未回答问题分开展示；没有证据不要虚构完整性或确信度。
- 实际打开 HTML 检查首屏、复述正文、所有导图节点、证据跳转及手机布局。若无法运行浏览器测试，至少进行结构和数据校验，不能声称已实测。
