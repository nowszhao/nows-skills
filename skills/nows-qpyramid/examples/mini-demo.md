# 最小虚构示例：用于理解输出格式，不作为事实来源

## 虚构素材（由本 Skill 作者构造）

> [段1] 我认为数据平台运维不该只从机器告警出发，还应该从失败的业务作业出发。机器正常，不代表作业能准时产出结果。
>
> [段2] 我们在一个项目中发现，许多作业延迟与资源争抢有关。但这个项目规模有限，不能直接外推到所有企业。
>
> [段3] 因此我建议先做作业级诊断，再尝试自动修复。我的团队还没有验证直接自动修复是否安全。

## 示例分析（展示，不声称已做行业核验）

**核心问题 Q0：** 数据平台运维 Agent 应该优先监控什么？

**作者总体答案：** 优先观察业务作业结果，先诊断后考虑修复。[段1–3]

**增量雷达**

- `以业务作业为入口，而非仅看机器告警`：`建议/方法 | 待外部核验 | 作者差异化视角 | 中`。依据是[段1]给出的结果导向理由；作者未证明它在所有客户场景都优于机器视角。
- `先诊断，再研究自治修复`：`建议/方法 | 待外部核验 | 作者差异化视角 | 弱`。作者明确表示安全性未验证，[段3]。

**问题金字塔**

```text
Q0 运维 Agent 应优先监控什么？→ 优先关注业务作业结果
├─ Q1 传统机器告警有什么不足？→ 机器正常并不保证作业及时完成
│  └─ Q1.1 有什么具体表现？→ 作业延迟可能来自资源争抢
└─ Q2 如何分阶段实现？→ 先做作业级诊断，再尝试修复
   └─ Q2.1 能否直接自动修复？→ 作者尚未验证安全性
```

**Q1.1 资源争抢是作业延迟的主要原因吗？** `[隐含重建]`

- 答案：作者只说它在某个项目中与许多延迟有关，没有主张适用于所有企业。[段2]
- 论证：单项目观察 → 局部相关性 → 不足以推断普遍因果。
- 原文依据：单个项目经验，[段2]。
- 标注：`解释/因果 | 待外部核验 | 具体新信息 | 中`；样本范围有限。
- 边界：无法从材料判断资源争抢是否为主因，也无对照数据。

**跨问题关系**：`Q1 [说明旧方法不足] → Q2 [提出处理顺序]`，关联依据[段1][段3]。

**下一步值得追问**：需要哪些生产指标比较机器告警与作业级诊断？何种机制能约束修复风险？
